## A. 人物扩展字段（世录展示数据）—— 最大缺口，必须先定

### A1. 扩展字段的载体

- **现状**：`Person` 表只有 `full_name / gender / birth_date / death_date / is_living / birth_place / death_place / migration_branch / avatar_url` 等；**没有字号、葬地、功名、传记正文、籍贯、岳家信息**。传记目前只存在于 `BioReview`（审核流：作者提交 → 审核）和 `PdfParseTemp`（临时导入表）。
- **选项**：
  - 方案 A：新建 `PersonBio` 附表（person_id 一对一），字段全部放附表；
  - 方案 B：直接给 `Person` 加列；
  - 方案 C：混合——常用/查询频繁字段（如葬地）放 Person，长文本（传记、轶事）放附表。
- **★推荐：方案 A（PersonBio 附表）**。理由：不膨胀主表（树谱/合并/性能热路径都读 Person）；与 PRD "传记附表" 术语一致；与树谱"卡片轻字段"理念天然隔离；后续加字段无迁移成本。
- ☐ 决策：

### A2. PersonBio 字段清单（逐项）

| 字段 | 类型 | 可空 | 说明/来源 | 备注 |
|---|---|---|---|---|
| `person_id` | BigInt | 否 | 主键 + FK → Person | |
| `courtesy_name` 字号 | String | 是 | 表字/号，手工录入 | 传统族谱标配 |
| `native_place` 籍贯 | String | 是 | 手工录入 | `birth_place` 是出生地，语义不同，不混用 |
| `burial_place` 葬地 | String | 是 | 手工录入 | `PdfParseTemp.burial_place` 导入时可回填 |
| `achievements` 功名 | Text | 是 | 科举/职官/荣誉，手工录入 | |
| `anecdotes` 轶事 | Text | 是 | 手工录入 | |
| `biography` 传记正文 | Text | 是 | 见 A3 来源决策 | 大段文字，树谱不展示 |
| `marital_notes` 配偶家世/岳家 | Text | 是 | 手工录入 | PRD §2.3 "岳家信息" |
| `adoption_note` 出继/兼祧标注 | Text | 是 | 见 E3 | |
| `premature` 早夭覆盖标记 | Boolean | 是 | 见 D1 | 空 = 按推导 |
| `updated_at` | DateTime | 否 | @updatedAt | |

- **★推荐：按上表执行**（字段名可按团队命名规范微调，语义不变）。
- ☐ 决策：

### A3. 传记正文（biography）的来源

- **现状**：`BioReview`（person_id, title, content, status=PENDING/APPROVED/REJECTED）是唯一传记内容载体，且带审核流；`PdfImportLog/PdfParseTemp` 导入的传记在临时表。
- **选项**：
  - ① 世录直接渲染 `BioReview.APPROVED` 的内容（不新增 biography 字段）；
  - ② `PersonBio.biography` 手工维护，与 BioReview 无关；
  - ③ 混合：BioReview 审核通过 → **自动回写** `PersonBio.biography`（PersonBio 为规范存储，BioReview 保留为"提交→审核"入口）。
- **★推荐：③ 混合（审核通过自动回写）**。理由：保留现有审核流不破坏；世录/PDF 只读一个稳定来源（PersonBio），不依赖审核状态；PDF 导出不掺入 PENDING 内容。
- ☐ 决策：

### A4. 传记录入入口（谁在哪个页面录入）

- **现状**：树谱侧栏 `PersonEditDrawer.vue` 只能编辑基础字段（姓名/性别/生卒/籍贯/迁徙分支）；`BioReviewPage` 是 admin 审核页；用户中心有 `BioReview` 提交入口（需核实）。
- **选项**：
  - ① 扩展 `PersonEditDrawer`（树谱编辑弹窗）加"传记/扩展资料"分组；
  - ② 册谱卷宗编辑页内提供"人物资料"入口；
  - ③ 独立"人物资料编辑页"。
- **★推荐：① + ② 组合**——树谱编辑弹窗加扩展资料 Tab（管理员最常用）；册谱世录条目旁提供"编辑资料"快捷入口；**不新增独立页面**。
- ☐ 决策：

### A5.（可选）世录是否展示"字辈"

- **现状**：`Xipai` 表（clan_id, generation, character）存字辈，PRD 世录字段清单未包含字辈。
- **★推荐：一期不展示**，世录字段严格按 PRD §2.3；二期若要做"按字辈列世系"再加。
- ☐ 决策：

## B. 排行（长幼）

### B1. 排行的唯一数据源

- **现状**：`FamilyChild.birth_order`（Int，同父母家庭内排行）是唯一排行字段；但树模块写入路径不维护它（见 H1）。
- **★推荐：确认 `FamilyChild.birth_order` 为唯一来源**，世录/树谱都读它；无记录时按 B3 降级。
- ☐ 决策：

### B2. 多家庭（过继/兼祧）排行歧义规则

- **现状**：一个人可出现在多个 `FamilyChild`（过继/兼祧/再婚家庭重组），各家庭排行不同。
- **选项**：
  - ① 取"出生家庭"（child_type=BIOLOGICAL 且创建最早的 FamilyChild）的排行为主；
  - ② 按出生日期全局排序生成排行（忽略家庭）；
  - ③ 全部显示，标注每个家庭内的排行。
- **★推荐：① 为主 + ③ 标注**——世录主排行用出生家庭排行；若存在非 BIOLOGICAL 家庭，世录文本追加"出继/兼祧 X 房"标注（用 `PersonBio.adoption_note` 或 `FamilyChild.child_type` 自动生成）。
- ☐ 决策：

### B3. 无 FamilyChild 记录时（存量/树模块老数据）降级

- **★推荐：不显示排行**（不猜），同辈排序退回出生日期升序；H2 回填后逐步消除该情况。
- ☐ 决策：

### B4. birth_order 的写入职责

- **★推荐：统一在"亲子关系写入函数"（H1）内自动计算**：新增子女时 birth_order = 该 FamilyUnit 现有子女数 + 1（与 `merge.service.ts` / `demo-seed.service.ts` 现有逻辑一致）。
- ☐ 决策：

## C. 房派

### C1. 房派来源：派生 vs 建表

- **现状**：无房派实体。`migration_branch`（迁徙分支）和 `Xipai`（字辈）语义都不是房派；**`family-book.service.ts` 已有成熟实现**：`groupByBranch()`（第 777-814 行）= 取始祖（generation 0）的子女（generation 1，非配偶）按出生日期排序，各成一支，命名"长房/二房/三房…"（`chineseBranchName`），`isDescendantOf()` 判断归属。
- **选项**：
  - ① 派生：复用/提取 `family-book` 的房支算法，世录生成时动态计算每人的房派归属；
  - ② 建 `Branch` 表 + `Person.branch_id`（手工维护）；
  - ③ 复用 `migration_branch`。
- **★推荐：① 派生（一期）**。理由：零 Schema 变更、与家庭图册口径一致；二期若出现"房派手工管理"强需求再上表（届时 `PersonBio` 加 `branch_id` 或新建表，兼容）。
- ☐ 决策：

### C2. 房派筛选的技术口径

- **★推荐**：世录生成时，为每人计算"房派根 id"（沿 parent 链回溯到第 1 代祖先，即始祖的直接子女 id）；卷配置 `config.branches` 存一组房派根 id，只输出命中的人员。与树谱"按房派折叠/筛选"（树谱 PRD 二期）共用同一口径。
- ☐ 决策：

## D. 早夭判定

### D1. 判定方式

- **现状**：无早夭标记字段。
- **选项**：
  - ① 纯推导：`death_date` 存在且享年 < 阈值（如 18 岁）判为早夭；
  - ② 纯字段：`PersonBio.premature` 布尔标记；
  - ③ 推导为主 + 字段覆盖。
- **★推荐：③**——默认推导（享年 < 18 岁），`PersonBio.premature` 可显式覆盖（如史料明确记载"早夭"但无死亡日期）。
- ☐ 决策：

### D2. 阈值可配置

- **★推荐**：阈值存 `BookVolume.config.premature_age`（世录卷级，默认 18）；不进全局 settings（避免跨卷耦合）。
- ☐ 决策：

### D3. 边界

- **★推荐**：在世（is_living=true）或无 death_date 一律不判早夭；"隐藏夭折"开关只影响渲染，不动数据（PRD §3.3 已定）。
- ☐ 决策：

## E. 过继 / 兼祧

### E1. 数据源确认

- **现状**：`FamilyChild.child_type`（BIOLOGICAL / ADOPTED / STEP / FOSTER）已存在且被 family-book、lineage-video、merge 等模块使用；树 API 不透出。
- **★推荐：确认 child_type 为唯一来源**，不做新表。
- ☐ 决策：

### E2. 树 API 透出契约（与树谱吊线图共用）

- **★推荐**：`getClanFullTree` / `getSubTree` 节点增加 `child_type`、`birth_order`、`child_family_id`（→ 可关联到 `FamilyUnit.wife_id`，吊线图"各妻子女分别分支"必需）。字段命名与前端 `GenealogyTree.vue` 现有 spouse 结构对齐。
- ☐ 决策：

### E3. "出继 / 兼祧"标注文本存哪

- **选项**：
  - ① 新增 `PersonBio.adoption_note`（手工/半自动）；
  - ② 世录渲染时根据 child_type 自动生成（"X 公三子，出继 Y 房"），不落库；
  - ③ 两者结合。
- **★推荐：③**——`adoption_note` 存人工补充信息，渲染时 child_type=非 BIOLOGICAL 自动追加"出继/收养"标识，两者拼接输出。
- ☐ 决策：

## F. 卷宗配置表 BookVolume

### F1. 表结构（新增）

```prisma
model BookVolume {
  id         BigInt   @id @default(autoincrement())
  clan_id    BigInt
  sort_order Int      @default(0)   // 卷顺序；PDF 严格按此输出
  title      String                 // 「卷一 谱序源流」
  type       String                 // document | shilu（文档卷 / 世录卷）
  content    String?  @db.Text      // 文档卷：富文本 HTML；世录卷：null
  config     Json?                  // 世录卷筛选（见 F3）；文档卷可 null
  created_by String
  created_at DateTime @default(now())
  updated_at DateTime @updatedAt

  @@index([clan_id, sort_order])
}
```

- **★推荐：按上表执行**。是否需要 `version` 历史表（卷宗内容版本）——**推荐二期**（一期用 `updated_at` + 操作日志即可，避免过度设计）。
- ☐ 决策：

### F2. 文档卷富文本存储格式

- **选项**：① HTML 字符串（wangEditor/quill 输出即 HTML）；② Json delta（ProseMirror 系）。
- **★推荐：① HTML（Text）**——编辑器选型自由、PDF 渲染直接（puppeteer 原生支持）、导出 Word 也有现成 HTML→docx 路线。
- ☐ 决策：

### F3. 世录卷 config 字段清单（确定版）

```jsonc
{
  "branches": ["<房派根 personId>", "..."],  // 空数组 = 全房派（见 C2）
  "include_female": true,                     // 是否收录本族女性（闺秀录卷 = false 反选）
  "hide_wife": false,                         // 隐藏妻子传记
  "hide_daughter": false,                     // 隐藏女儿记录
  "hide_son_in_law": false,                   // 隐藏女婿记录
  "hide_premature": false,                    // 隐藏夭折（D1）
  "premature_age": 18,                        // 早夭阈值（D2）
  "layout": "su",                             // su=苏式 | ou=欧式（二期）| shixi_table=世系表开本（PR#1 新增）
  "page_gen_count": 5,                        // 世系表专属：每页并列世代数，默认 5
  "show_generation_connector": true,          // 世系表专属：是否绘制顶端连接线+小圆圈
  "surname_color": "#b22222",                 // 世系表专属：人物名颜色，默认红色
  "exclude_person_ids": []                    // 世录黑名单（可选：排除指定人物）
}
```

- **★推荐：按上表执行**，与树谱过滤开关语义一一对应（树谱 PRD §2.4 / 册谱 PRD §2.3）。

- ☐ 决策：

## H. 数据一致性修复（双写）—— 硬前提

### H1. 统一亲子关系写入入口

- **现状**：
  - `tree.service.createPerson(parent_id)`：写 `Person + PersonAncestry`，**不写 FamilyChild**；
  - `family-relation.service.addChild`：写 `Person + FamilyUnit + FamilyChild + ChildCustodyRecord + FamilyRelationChange`，**不写 PersonAncestry**。
  → 双方数据不同步，"树谱↔册谱数据完全一致"（两份 PRD 的共同验收项）不成立。
- **★推荐**：新增/收敛一个事务级函数 `createParentChildRelation(tx, parentId, childId, familyId?, childType?)`，内部同时维护 `PersonAncestry`（含 self-record 与全部祖先链）+ `FamilyChild`（含 birth_order 自动编号）；tree 与 family-relation 两处都改调它。`moveSubTree`、归宗合并（`merge.service`）同样走该函数/同步维护 FamilyChild。
- ☐ 决策：

### H2. 存量数据回填

- **现状**：历史数据存在"有 PersonAncestry 无 FamilyChild"（树模块创建）和"有 FamilyChild 无 PersonAncestry"（用户中心创建）两类缺口。
- **★推荐**：写一次性回填脚本（幂等）：
  - 对每条缺 FamilyChild 的 depth=1 亲子对：优先挂到已存在的匹配 FamilyUnit（父母双方都在）；无则**新建单亲 FamilyUnit**（schema 中 `husband_id`/`wife_id` 均可空，已支持）；
  - 对每条缺 PersonAncestry 的 FamilyChild：按 B1 逻辑重建闭包表记录；
  - 校验项：回填后 `PersonAncestry(depth=1)` 与 `FamilyChild` 两表亲子对集合一致。
- ☐ 决策：

### H3. 一致性验收口径

- **★推荐**：验收脚本 = `SELECT` 两表亲子对差集为 0；纳入树谱/册谱共同验收项（PRD §8-1）。
- ☐ 决策：

## I. 其他技术决策

### I1. 全文检索方案

- **★推荐：一期用 PostgreSQL `LIKE/ILIKE` + 卷内过滤**（单族人物 < 5000 规模足够，配合虚拟列表）；二期如有跨族/性能需求再上 `pg_trgm` 或 ES。不新增中间件。
- ☐ 决策：

### I2. PDF 字体（繁体/生僻字不乱码）

- **★推荐：预打包思源宋体子集（常用 3500 字 + 追加族谱生僻字）**，随 worker 或 print 模块发布；运行时按需子集化（如 fontmin）可作为二期优化。验收：导出 PDF 抽查繁体/生僻字无豆腐块。
- ☐ 决策：

### I3. 世录排序键

- **★推荐**：辈分 = `PersonAncestry` 中相对族根深度（`depth`）；同辈 = `birth_order`（B1）→ 缺失时出生日期；与 tree 的 `generation` 口径一致（family-book 用 generation 0/1 分代，可对齐）。
- ☐ 决策：
