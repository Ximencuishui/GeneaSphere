## 一、总体结论

**合理性：合理。** 两份文档的核心设计思想——"单数据源、配置驱动、视图隔离、树谱看关系/册谱看档案"——与项目现状高度契合，且与《树谱模块 PRD》在"禁止两套独立数据存储、双向跳转、过滤开关语义"上完全一致，属于可落地的产品设计。一期/二期划分务实（一期是录入→生成→导出→联动的核心闭环）。

**可实现性：可实现，但开工前必须先解决 3 类前置项：**

| 类别 | 数量 | 内容 |
|---|---|---|
| Schema 缺口 | 2 项 | ① 世录展示字段（字号/葬地/功名/传记/岳家/籍贯）在现有表中**大部分不存在**；② 册谱卷宗配置表、批注表需新建 |
| 数据一致性问题 | 1 项 | 树模块与柔性家庭关系模块**两条写路径不同步**（详见 §五） |
| 产品决策 | 2 项 | ① 底部 Tab【树谱\|册谱\|设置】与现有 App 页面结构冲突；② "传记附表"的录入入口未定义 |

> 结论一句话：**"一册双态、数据同源"的理念在现有数据结构上完全站得住，但世录渲染所依赖的人物扩展字段目前是空的，且两个 PRD 都默认这些字段存在——这是最大的隐性缺口。**

## 二、需求合理性评审

### 2.1 做得好的点

1. **单数据源原则贯穿始终**（PRD §2.1、§3.1–3.3）：人物只存一份，册谱是编排视图。这与现有实现"树谱实时读 Person/FamilyUnit/PersonAncestry"完全同构，落地成本低。
2. **卷宗结构（文档卷 + 世录卷）设计聪明**：手工史料（谱序/祖训/艺文）与自动生成的人物条目分离，既保留了传统族谱体例，又避免管理员重复抄写人物（PRD §2.2）。
3. **过滤开关只控渲染、不碰数据**（PRD §3.3）：安全边界清晰，与树谱过滤开关逻辑对齐（前端设计文档 §4.3）。
4. **异常处理考虑周全**（PRD §4.3）：删除人物自动跳过并提示、OCR 乱码保留原文、PDF 超时提示拆分导出，都是真实场景。
5. **前端设计文档质量高**：组件拆分（BookHeader/BookSidebar/BookArticle/BookFamilyList/BookFilter/BookExport/PersonPop/LinkToTree）高内聚低耦合；印刷级样式规范（象牙白底、宋体、1.8 倍行高、首行缩进 2 字符）直接可开发；移动端三档断点（≥1200 / 768–1200 / <768）合理。
6. **一期/二期划分合理**：一期（卷宗管理、苏式世录、PDF 整本导出、双向跳转、基础过滤）就是最小可用闭环；欧式排版、批注、分享、Word 等放二期符合"先跑通再增强"。

### 2.2 需要澄清 / 存疑的点

1. **"传记附表"录入入口缺失（最重要）**
   PRD §2.1 把"传记附表"列为数据源，但全文没有定义**管理员在哪里录入**传记、字号、葬地、功名。现有 `Person` 表没有这些字段（见 §三），`BioReview` 是"传记审核流"（作者提交→审核），不是规范存储。需要决策：① 新建 `PersonBio` 附表并配套"人物资料/传记编辑页"；② 还是扩展 `Person` 列。**建议一期就包含录入入口，否则世录卷无内容可渲染。**

2. **排行（长幼）的定义源**
   PRD §2.1.4 "同辈按长幼排行"：现有排行存于 `FamilyChild.birth_order`（同父母内排行），且**树模块的写入路径不维护 FamilyChild**（见 §五-2）。另外过继/兼祧的人可能同时出现在多个家庭，排行会出现歧义——需要定规则（如取出生日期排序、或取"主要家庭"排行）。

3. **"房派"无对应数据实体**
   PRD 多处使用房派（§2.1.4 按房派分组、§2.2 世录卷按房派筛选、§2.5 房派划分内容）。现有 Schema 只有 `migration_branch`（迁徙分支，语义不符）和 `Xipai`（字辈，也不是房派）。需决策：按"始祖各子的后代"派生房派，还是新增房派字段/表。**这与树谱 PRD 的"房派折叠/筛选"是同一个缺口。**

4. **"夭折"判定无依据**
   PRD §2.6.3 和前端文档 §4.3 的"隐藏夭折"：现有无早夭标记，只能按死亡年龄阈值推导（如享年 < 18），阈值需定义；或加字段。

5. **底部 Tab【树谱 | 册谱 | 设置】是产品结构决策**
   两份 PRD 都假定存在全局底部 Tab。但现有 App 是"顶部导航 + `/tree/:clanId` 独立页（`AdminLayout`/用户中心各自为阵）"，没有全局 Tab 栏。这要么是"改造 App 壳"（影响面大），要么是把树谱/册谱做成一个**新入口下的双 Tab 模块**。需要产品拍板，不能直接照搬。

6. **Word 导出无现成底座**
   项目无 docx 依赖（web 仅有 html2canvas；server 无 docx 库）。Word 导出需要新增依赖 + 排版映射，且 PRD 一期清单里没有它——**建议明确 Word 为二期**（PRD §2.5 功能表与 §7 分期存在轻微不一致，功能表把 Word 放在基础功能里）。

7. **欧式排版与移动端冲突**
   欧式世代格子对齐在 <768px 小屏上会非常拥挤，前端设计文档 §6.3"禁止横向滚动"与之矛盾。建议欧式二期实现时限定 ≥768px 或做降级（退回苏式/列表）。

## 三、数据可行性逐条对照（世录字段 ↔ 现有 Schema）

| 册谱需求字段/能力 | 现有存储 | 结论 |
|---|---|---|
| 姓名 / 性别 / 生卒 | `Person.full_name / gender / birth_date / death_date / is_living` | ✅ 已具备 |
| 迁徙地点 | `Person.migration_branch`、`MigrationEvent` | ✅ 已具备 |
| 排行 | `FamilyChild.birth_order` | ⚠️ 有字段，但树写路径不维护（§五-2） |
| 子嗣名单 | `PersonAncestry`（父子）+ `FamilyChild` | ✅ 可查（排行需 join FamilyChild） |
| 配偶（含继配/妾） | `FamilyUnit.marriage_order / union_type / end_reason / is_current` | ✅ 已具备，多配偶天然支持 |
| 过继 / 兼祧标记 | `FamilyChild.child_type`（BIOLOGICAL/ADOPTED/STEP/FOSTER） | ⚠️ 有字段，但树 API 不透出（与树谱吊线图同一缺口） |
| 图片（画像/墓碑） | `MediaArchive` + `MediaPersonLink` | ✅ 已具备 |
| 人物传记正文 | `BioReview`（审核流） | ⚠️ 可复用为来源，或新建 `PersonBio` 规范存储 |
| **字号（表字/号）** | ❌ 无字段 | **需新增** |
| **葬地** | ❌ `Person` 无 burial 字段（仅 `PdfParseTemp` 临时表有） | **需新增** |
| **功名 / 轶事** | ❌ 无字段 | **需新增** |
| **籍贯 / 岳家信息** | ❌ 无字段（birth_place 近似籍贯但语义不同） | **需新增** |
| 卷宗配置（卷标题/类型/排序/筛选） | ❌ 无 | **需新建 `BookVolume` 表** |
| 批注 | ❌ 无 | **需新建表** |
| 全文检索 | 无独立索引（`SearchPost` 是寻亲帖，无关） | 需新增（卷宗内容 + 人物字段） |
| PDF 导出 | `print` 模块 + `worker/puppeteer_render.js`（HTML→PDF） | ✅ 底座在，需扩展为整本册谱排版 |
| Word 导出 | ❌ 无 docx 依赖 | 需新增依赖 |
| 只读权限 | `ClanMember.role`（VIEWER/EDITOR/ADMIN/OWNER）+ `adminService.requireAdmin` | ✅ 已具备 |
| 人物删除后跳过 | `Person.deleted_at` 软删除 | ✅ 已具备 |

## 四、必须的 Schema 变更清单（最小集）

```prisma
// 1) 册谱卷宗配置表（新增）
model BookVolume {
  id          BigInt   @id @default(autoincrement())
  clan_id     BigInt
  sort_order  Int      @default(0)      // 卷顺序，PDF 按此输出
  title       String                    // 「卷一 谱序源流」
  type        String                    // document | shilu（文档卷 / 世录卷）
  content     Json?                     // 文档卷：富文本内容（含图片）；世录卷：null
  config      Json?                     // 世录卷筛选：{branches[], include_female, hide_wife, hide_daughter, hide_son_in_law, hide_premature, layout: 'su'|'ou'}
  created_by  String
  created_at  DateTime @default(now())
  updated_at  DateTime @updatedAt
  @@index([clan_id, sort_order])
}

// 2) 批注表（新增，二期）
model BookAnnotation {
  id          BigInt   @id @default(autoincrement())
  volume_id   BigInt
  anchor      String                    // 段落锚点（世录条目 id / 文本 hash）
  note        String
  created_by  String
  created_at  DateTime @default(now())
}

// 3) 人物传记附表（新增，解决世录字段缺口 —— 推荐方案 A）
//    理由：不膨胀 Person 主表；与 PRD "传记附表" 术语一致；BioReview 保留为审核流
model PersonBio {
  person_id       BigInt   @id
  courtesy_name   String?  // 字号
  native_place    String?  // 籍贯
  burial_place    String?  // 葬地
  achievements    String?  // 功名
  anecdotes       String?  // 轶事
  biography       String?  // 传记正文（或复用 BioReview.APPROVED 作为来源）
  marital_notes   String?  // 岳家/配偶家世备注
  premature       Boolean? // 早夭标记（可选，否则用死亡年龄推导）
  updated_at      DateTime @updatedAt
  person          Person   @relation(fields: [person_id], references: [id], onDelete: Cascade)
}
```

> 若不想加表，方案 B：把上述字段直接加到 `Person`（`courtesy_name / burial_place / achievements / biography / native_place`…）。推荐方案 A：语义清晰、不动主表、便于和"树谱卡片轻字段"隔离。

## 五、必须的后端工作

1. **册谱模块（新）**：`BookVolume` CRUD + 排序；**世录生成接口**（读 Person + FamilyUnit/FamilyChild + PersonAncestry + PersonBio + MediaPersonLink，按辈分（闭包表深度）降序 → 同辈按排行/出生日期升序，套用卷配置过滤，输出苏式/欧式渲染数据）；全文检索；批注 CRUD；PDF（单卷/整本，接 puppeteer worker 或 print 模块扩展）；Word（二期，新增 docx 依赖）；卷宗配置 JSON 导入导出；只读权限（VIEWER 只读，ADMIN/OWNER 可编辑）。
2. **树 API 增强（与树谱吊线图共用缺口）**：`getClanFullTree` / `getSubTree` 返回的节点透出 `child_type`（亲生/过继/收养/继子女）、`birth_order`（排行）、`child_family_id → wife_id`（子女归属哪段婚姻，吊线图"各妻子女分别分支"必需）。
3. **双写一致性修复（关键，别漏）**：
   - `tree.service.createPerson(parent_id)` 只写 `PersonAncestry`，**不写 FamilyChild** → 树上添加的人物没有排行/过继类型；
   - `family-relation.service.addChild` 只写 `FamilyChild`，**不写 PersonAncestry** → 用户中心添加的子女可能不进闭包表、树上看不到；
   - 需统一为事务内双写 + 存量数据回填脚本，否则"树谱↔册谱数据完全一致"（两个 PRD 的验收项）不成立。
4. **双向跳转**：册谱→树谱 = 携带 personId，前端复用现有搜索高亮/聚焦逻辑；树谱→册谱 = 世录条目锚点（`BookVolume + 世录 item id`），滚动 + 闪烁高亮。

## 九、风险与建议

1. **最大风险：世录字段缺失 + 排行/房派/早夭定义不明确。** 建议动工前先产出一份《册谱数据模型决策清单》（字段放 Person 还是 PersonBio？房派怎么来？早夭阈值？排行歧义规则？），一次拍板，避免返工。
2. **建议一期范围严格收敛**：只做苏式、不做 Word、批注二期（PRD 已如此划分）；把"人物资料/传记录入入口"补进一期，否则世录卷没有内容。
3. **双写一致性修复应排在最前面**：它是"树谱↔册谱数据完全一致"验收项的硬前提。
4. **底部 Tab 需要产品决策**：建议做成"族谱双视图"新入口（`/genealogy/:slug` 下树谱/册谱两个子 Tab），不动现有顶部导航与用户中心结构，影响面最小。
5. **PDF 字体嵌入**：繁体/生僻字防乱码需嵌入思源宋体子集（前端设计文档 §九-3 已提），注意字体资产体积（可用按需子集化）。
