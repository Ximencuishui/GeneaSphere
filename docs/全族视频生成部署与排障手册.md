# 全族视频生成部署与排障手册

本文给部署和联调的人使用。链路是：管理端创建大事件或迁徙视频项目 → Node 写入 `heavy_jobs`（`type = video`）→ 线下 `worker/worker.py` 轮询领取 → Pillow 画 1920×1080 PNG → `ffmpeg` 的 `libx264` 合成 MP4 → 预签名 PUT 到 COS，或拷贝到本地 `STORAGE_PATH` → `POST /api/jobs/callback` 把项目标成已完成或失败。

涉及文件：

- `worker/worker.py`（`handle_video`、`_render_slide`、`_assemble_mp4`、`_publish_video`、`process_job`、`log`）
- `apps/server/src/jobs/jobs.controller.ts`、`jobs.service.ts`、`clan-video-job.ts`
- `apps/server/src/clan-event-video/clan-event-video.service.ts`
- `apps/server/src/clan-migration-video/clan-migration-video.service.ts`
- `apps/server/src/cos/cos.service.ts`
- `apps/web/src/views/admin/EventVideoPage.vue`、`MigrationVideoPage.vue`

`worker/` 目录没有 README。安装方式和常量以 `worker.py` 文件头、`worker/requirements.txt` 为准。

## 一、依赖与部署清单

### 1. Python 依赖

`worker/requirements.txt` 原文：

```text
requests>=2.28.0
Pillow>=9.0.0
```

`worker.py` 文件头写的用法是：

1. 修改文件里的 `LIGHTHOUSE_URL` 和 `INTERNAL_API_KEY`。
2. 安装依赖：`pip install requests`。
3. 运行：`python worker.py`。

视频画帧会 `import PIL`。缺 Pillow 时 `_render_slide` 抛出 `RuntimeError: 幻灯片渲染需要 Pillow: pip install Pillow`。部署视频时按 requirements 安装，在 `worker` 目录执行：

```bash
pip install -r requirements.txt
python worker.py
```

`worker/package.json` 的依赖只有 `puppeteer`（`^22.0.0`），给 Puppeteer 渲染任务用。全族视频这条链路不执行 `npm install`，也不调用 `puppeteer_render.js`。

Worker 启动后，`log()` 同时打到标准输出和 `worker/worker.log`（与 `worker.py` 同目录）。临时下载目录是 `worker/work`。每一条视频任务的帧和 `out.mp4` 放在 `worker/work` 下的临时目录，`handle_video` 的 `finally` 会 `shutil.rmtree` 删掉，失败后磁盘上不再留下 PNG 序列。

### 2. 系统依赖：ffmpeg 必须带 libx264

必须安装 `ffmpeg`，并且可执行文件在 PATH 里。`_require_ffmpeg`（约第 266–270 行）只用 `shutil.which("ffmpeg")`。代码里没有 ffmpeg 路径环境变量。找不到时抛出：

```text
RuntimeError: ffmpeg 不可用，无法生成视频
```

合成命令在 `_assemble_mp4`（约第 429–448 行）。参数是一个 list，交给 `subprocess.run`（未传 `shell`，即为 `shell=False`）。编码器写死为 `libx264`，像素格式写死为 `yuv420p`。没有使用 `mpeg4`，也没有 `-c copy`。机器上的 ffmpeg 必须带 `libx264`，并且带上下面这条 `-vf` 里用到的滤镜：`fps`、`format`，以及按风格三选一的 `colorchannelmixer`、`eq`、`hue`。

实际拼接（`rate = 1 / 每条秒数`，`pattern` 为临时目录里的 `frame_%04d.png`，反斜杠会换成正斜杠）：

```text
ffmpeg -y -framerate <rate> -start_number 0 -i <frame_%04d.png>
  -vf fps=30,<风格滤镜>,format=yuv420p
  -c:v libx264 -pix_fmt yuv420p -movflags +faststart <out.mp4>
```

风格滤镜来自 `CLAN_VIDEO_VF`（约第 231–235 行），`style` 先经 `_normalize_video_style` 收成这三档之一，非法值当成 `nostalgic`：

| style | 每条默认秒数 | `-vf` 中的风格段 |
| --- | --- | --- |
| nostalgic | 8 | `colorchannelmixer=.393:.769:.189:0:.349:.686:.168:0:.272:.534:.131` |
| modern | 6 | `eq=contrast=1.08:saturation=1.25:brightness=0.02` |
| solemn | 10 | `hue=s=0,eq=contrast=1.12:brightness=-0.03` |

总时长上限 `CLAN_VIDEO_MAX_SECONDS = 600`。事件很多时单帧秒数会被压到 `600 / 条数`。输入是图片序列（`-framerate` + `-i frame_%04d.png`），不是 concat 解复用器。命令里没有音频输入。

画面由 `_render_slide` 固定画成 `1920×1080`（约第 379 行），宽和高都是偶数。命令本身没有再做偶数对齐的 scale 滤镜。`format=yuv420p` 和 `-pix_fmt yuv420p` 要求宽、高都能被 2 整除；当前帧尺寸满足这个要求。

### 3. 中文字体

`_load_cjk_font`（约第 273–282 行）按 `_CJK_FONTS`（约第 236–244 行）的顺序找文件。文件不存在就跳过；`ImageFont.truetype` 抛错也跳过，继续下一个。全部失败时返回 `ImageFont.load_default()`，函数本身不抛错，幻灯片会继续保存，任务可以成功完成。

尝试顺序：

1. `C:\Windows\Fonts\msyh.ttc`（微软雅黑）
2. `C:\Windows\Fonts\msyhbd.ttc`（微软雅黑 Bold）
3. `C:\Windows\Fonts\simhei.ttf`（黑体）
4. `C:\Windows\Fonts\simsun.ttc`（宋体）
5. `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`
6. `/usr/share/fonts/truetype/noto/NotoSansCJK-Regular.ttc`
7. `/usr/share/fonts/truetype/wqy/wqy-microhei.ttc`

机器上没有这些字体时，会落到 `ImageFont.load_default()`。这条分支不会让任务失败。`load_default()` 的位图字体不含中文，标题、地点、描述里的汉字会画成方块或 `.notdef`，看起来像没字。Windows 部署机保留雅黑、黑体或宋体即可；Linux 需要装上表中的 Noto Sans CJK 或文泉驿微米黑，路径必须与上表一致，代码不会搜索其他目录。

`_render_slide` 用到的字号是标题 64、年月地点 36、正文 32、片头标题 28，都走同一个加载函数。

### 4. 要改的常量与环境变量

Worker 侧这两个值是 `worker.py` 顶部的常量，进程不会去读同名环境变量：

| 常量 | 代码默认值 | 作用 |
| --- | --- | --- |
| `LIGHTHOUSE_URL` | `http://localhost:3001` | 拼出 `{LIGHTHOUSE_URL}/api/jobs/pending` 和 `/api/jobs/callback` |
| `INTERNAL_API_KEY` | `geneasphere-internal-key-change-me` | 请求头 `X-Internal-Key` |

Node 监听端口是 `process.env.PORT`，缺省 **3101**（`apps/server/src/main.ts`）。Worker 默认地址是 **3001**。同一台机器联调时，把 `LIGHTHOUSE_URL` 改成 API 实际地址（本地一般是 `http://localhost:3101`）。文件头注释写明上线后改为 `https://xungenlu.cn`。

Node 侧：

| 变量 | 代码中的默认或判断 | 作用 |
| --- | --- | --- |
| `INTERNAL_API_KEY` | 未设置时 `geneasphere-internal-key-change-me`（`jobs.controller.ts` 约第 17 行） | 与请求头 `x-internal-key` 全字匹配。Worker 常量必须和这里的最终值相同 |
| `STORAGE_PATH` | 未设置时 `<进程 cwd>/storage/media` | 本地成片目录；Worker 读 `/media/` 配图时也会读这个环境变量 |
| `STORAGE_DRIVER` | 未设置时 `local` | `CosService.getDriverType()` 返回这个值。只有它等于 `cos` 时，`resolveClanVideoDestination` 才会去要预签名 |
| `COS_ENABLED` | 字符串 `true` 时 `CosService` 选用腾讯云驱动 | 它不改变 `getDriverType()`。只开 `COS_ENABLED`、`STORAGE_DRIVER` 仍是 `local` 时，视频任务走本地落盘 |
| `TENCENT_CLOUD_SECRET_ID` / `TENCENT_CLOUD_SECRET_KEY` | 缺一则 COS 客户端不就绪 | 预签名会抛 `COS 客户端未就绪`，创建任务时退回本地 |
| `TENCENT_CLOUD_REGION` | `ap-guangzhou` | 预签名里的 Region |
| `TENCENT_CLOUD_APPID` | 空 | 非空时桶名变成 `{bucket}-{appId}` |
| `COS_HOT_BUCKET` | `xungenlu-hot` | PUT 预签名使用热桶 |
| `COS_COLD_BUCKET` | `xungenlu-cold` | 本链路的 PUT 不用冷桶 |
| `CDN_DOMAIN` | `cdn.xungenlu.cn` | 成功走 COS 时 `public_url` 为 `https://{CDN_DOMAIN}/videos/{kind}/{projectId}.mp4` |

预签名在 `TencentCosDriver.getPresignedPutUrl`（约第 208–235 行）：`Method: PUT`，默认有效期 21600 秒，签名不含 `Content-Type`。Worker 的 `requests.put` 只提交文件字节，不另设 Content-Type，与这条签名一致。

对象键由 `clanVideoObjectKey` 生成：`videos/clan-event/{projectId}.mp4` 或 `videos/clan-migration/{projectId}.mp4`。

## 二、联调与排障

页面状态文案以两个 Vue 文件里的 `statusLabel` 为准：

| 项目 `status` | 标签 |
| --- | --- |
| `queued` | 排队中 |
| `processing` | 生成中 |
| `completed` | 已完成 |
| `failed` | 失败 |

创建成功时的气泡是「视频项目已创建，正在生成中…」。那是 `ElMessage`，不是列表标签。当前创建逻辑把项目写成 `queued`，领取任务时只把 `heavy_jobs.status` 改成 `processing`，不会把视频项目改成 `processing`。所以生成过程中列表会一直显示「排队中」，直到回调把项目写成 `completed` 或 `failed`。标签变成「生成中」需要项目行本身是 `processing`，这条链路的写库代码不会那样写。

两个页面都是每 5 秒轮询一次：大事件 `GET /api/clan-event-videos/{slug}/{projectId}`，迁徙 `GET /api/clan-migration-videos/{slug}/{projectId}`。看到 `completed` 或 `failed` 就停止。轮询请求出错被吞掉（`catch` 里是空的或注释 `ignore polling errors`），页面不会因此改状态。

### 1. 前端一直「排队中」

现象：列表标签停在「排队中」，气泡已经提示正在生成，过了很久既不是「已完成」也不是「失败」。

代码里的原因：项目在 `ClanEventVideoService.create` / `ClanMigrationVideoService.create` 里以 `queued` 入库，并插入一条 `status: pending` 的 `heavy_jobs`。Worker 的 `main` 每 5 秒调用 `GET {LIGHTHOUSE_URL}/api/jobs/pending`，不带 `type`。`fetchNextPending` 取 `createdAt` 最早的一条 `pending`。Worker 没启动、连不上、鉴权失败，或更早的 OCR / Puppeteer 任务占着队列时，这条视频会留在 `pending`，项目保持 `queued`。任务一旦被领走，`heavy_jobs` 变为 `processing`；若随后回调没打成功，项目仍然是 `queued`，而且 `pending` 接口不会再次发出已经是 `processing` 的任务。

排查：

1. 看 Worker 进程是否在跑，以及标准输出 / `worker/worker.log` 里有没有 `Worker 启动` 和 `Lighthouse URL: ...`。
2. 核对 Worker 常量 `LIGHTHOUSE_URL` 是否指向正在听的 API。连不上时日志是 `⚠ 无法连接 Lighthouse ({LIGHTHOUSE_URL})，5s 后重试...`。默认 `http://localhost:3001` 和 API 默认端口 3101 不一致时就会一直这样。
3. 核对鉴权。Worker 请求头是 `X-Internal-Key`，值是文件里的 `INTERNAL_API_KEY`。Node 读的是环境变量 `INTERNAL_API_KEY`，未设置时默认 `geneasphere-internal-key-change-me`，比较在 `checkInternalAuth`。不一致时接口返回 HTTP 401，正文 `Unauthorized`。Worker 日志是 `⚠ HTTP 错误: ...`。
4. 在数据库看这条 `heavy_jobs`：仍是 `pending` 说明还没领到；已是 `processing` 且 Worker 日志有 `开始处理任务` 但没有 `任务完成` 或 `任务失败`，说明回调没落到 Node（回调地址同样受 `LIGHTHOUSE_URL` 和 `X-Internal-Key` 影响）。
5. 若 Worker 正在打其他 `job_id` 的日志，视频会继续「排队中」，因为 `pending` 按创建时间取最早一条，不按 `type=video` 过滤。

### 2. 前端「失败」，页面上看不到原因

现象：`statusLabel` 为「失败」，操作列和气泡都是「生成失败，请稍后重试」。页面没有具体错误句子。

代码里的原因：Worker 的 `process_job`（约第 633–641 行）捕获任意异常，先 `log` 再回调。日志原文是：

```text
❌ 任务失败: {job_id} - {异常类名}: {异常信息}
```

紧接着是 `traceback.format_exc()`。回调体为 `status: failed`，`error_message` 为 `{异常类名}: {异常信息}`。

Node `JobsController.callback` 在 `status === 'failed'` 时调用 `failJob(job_id, error_message || 'Unknown error')`。`failJob`（约第 140 行）打的是：

```text
任务失败: {jobId} - {errorMessage}
```

Logger 上下文是 `JobsService`。同一函数把 `heavy_jobs.errorMessage` 写成这段话，再由 `markClanVideoFailed` 只把项目 `status` 改成 `failed`。代码注释写明视频项目还没有 `error_message` 列，所以前端无法显示 Worker 抛出的那句原因。`markClanVideoFailed` 写库失败时另有一条 `视频项目失败状态未写入：...`，任务行仍然是 failed。

排查：

1. 打开 `worker/worker.log`，搜 `❌ 任务失败` 和上面的堆栈。常见句子包括 `ffmpeg 不可用，无法生成视频`、`ffmpeg 生成失败: ...`、`视频任务缺少事件快照`、`幻灯片渲染需要 Pillow: pip install Pillow`。
2. 打开 Nest 日志，搜 `任务失败:`。这里的后半段应与 Worker 回调的 `error_message` 一致。
3. 若 Worker 有 `❌ 任务失败` 而 Nest 没有 `任务失败`，回调本身失败了，继续在 Worker 日志里看 `⚠ HTTP 错误` 或 `⚠ 未知错误`，并核对 `INTERNAL_API_KEY`。
4. 完成回调里如果没有有效视频地址，走的是 `completeJob` 而不是 `failJob`：任务行是 completed，项目仍会被标成 failed，Nest 日志是 `视频项目 {projectId} 完成回调没有视频地址，已标为 failed`。这种失败在 Worker 侧可能已经打过 `✅ 任务完成`。

### 3. Python 报 ffmpeg

现象：项目变为「失败」。Worker 日志里是 `RuntimeError: ffmpeg 不可用，无法生成视频`，或 `RuntimeError: ffmpeg 生成失败:` 后面带一段 ffmpeg 输出。

代码里的原因：`handle_video` 在画帧前调用 `_require_ffmpeg`。合成时 `_assemble_mp4` 把命令以 list 传给 `subprocess.run(..., capture_output=True, text=True)`。返回码非 0，或 `out.mp4` 不存在，或文件大小为 0，就取 stderr（没有则用 stdout）的最后 500 个字符，抛出 `ffmpeg 生成失败: {这段文字}`。尺寸来自 Pillow 的 1920×1080，命令要求 `libx264` + `yuv420p`。没有在命令里追加偶数缩放滤镜。

按命令里真实参数，常见报错和改法：

| 日志里能看到的句子 | 改法 |
| --- | --- |
| `ffmpeg 不可用，无法生成视频` | 安装 ffmpeg，保证执行 `ffmpeg` 时能在 PATH 里找到。代码不读单独的路径变量 |
| stderr 中的 `Unknown encoder 'libx264'` | 换成带 `libx264` 的 ffmpeg 构建。命令写死 `-c:v libx264`，默认 mpeg4 构建过不了这一步 |
| stderr 中的 `No such filter`，点名 `eq`、`hue`、`colorchannelmixer`、`fps` 或 `format` | 换成带这些滤镜的构建。`-vf` 全文是 `fps=30,` 加上表中的风格段，再加 `,format=yuv420p` |
| stderr 中的 `not divisible by 2` / `height not divisible` / `width not divisible` | `yuv420p` 要求偶数宽高。当前 `_render_slide` 画的是 1920×1080，正常不应出现。若出现，说明 ffmpeg 读到的帧不是这个尺寸，先核对 Worker 是否为这份 `worker.py`，并在任务还没结束时看临时目录里的 `frame_0000.png`（成功或失败后目录会被删掉） |
| `ffmpeg 生成失败:` 且提到找不到 `frame_` 或输入 | 输入是 `-start_number 0` 的 `frame_%04d.png` 序列。帧由 `enumerate` 从 0 连续编号。临时目录在 `worker/work`，前缀 `video_{jobId}_` |

改法停留在安装、PATH 和构建能力。手册不改命令，也不增加代码里没有的滤镜。

### 4. COS 预签名失败后退回本地

现象：视频最后能播放或不能播放，地址要么是 CDN 上的 mp4，要么是 `/media/videos_clan-event_{id}.mp4`、`/media/videos_clan-migration_{id}.mp4`。有时文件在磁盘上，浏览器打开 `/media/...` 却是 404。

代码里的原因分两段。

创建任务时 `resolveClanVideoDestination`（`clan-video-job.ts` 约第 70–89 行）决定 payload：

- `getDriverType()` 不是 `cos`（即 `STORAGE_DRIVER` 不是 `cos`），或没有注入 `CosService`：直接用本地目的地，payload 不带 `upload_url`。
- 驱动是 `cos` 时调用 `getPresignedPutUrl(videos/{kind}/{projectId}.mp4)`，再用 `getCdnUrl` 得到公开地址。两者去空白后都非空，payload 带上 `upload_url` 和 CDN `public_url`。`storage_path` 仍然是本地路径。
- 预签名抛错（例如 `COS 客户端未就绪`、`生成上传地址失败: ...`），或 `upload_url` / `public_url` 有一个为空：`catch` 或判断后退回本地，不把 `upload_url` 写入 payload。Nest 侧对应日志还有 `未配置腾讯云 COS 密钥（TENCENT_CLOUD_SECRET_ID/KEY），COS 驱动不可用`。

本地目的地由 `localClanVideoDestination`（约第 51–61 行）生成。斜杠改成下划线：

- `public_url`：`/media/videos_clan-event_{projectId}.mp4` 或 `/media/videos_clan-migration_{projectId}.mp4`
- `storage_path`：`path.join(STORAGE_PATH 或 <cwd>/storage/media, 上面的文件名)`

COS 成功时 `public_url` 来自 `getCdnUrl`：配置了 `CDN_DOMAIN` 时为 `https://{CDN_DOMAIN}/videos/{kind}/{projectId}.mp4`（默认域名 `cdn.xungenlu.cn`）。`CDN_DOMAIN` 为空字符串时改为 `https://{热桶}.cos.{region}.myqcloud.com/videos/{kind}/{projectId}.mp4`。

Worker `_publish_video`（约第 453–479 行）的落盘：

- payload 里有非空 `upload_url`：`requests.put` 上传文件。成功后返回 `public_url`（CDN 形态）。PUT 失败（`raise_for_status`）会抛错，任务失败，此时不会再拷贝到 `storage_path`。上传成功但缺少 `public_url` 时抛出 `已上传成片，但任务没有可访问地址 public_url`。
- 没有 `upload_url`，且 `storage_path`、`public_url` 都是非空字符串：`os.makedirs` 父目录后 `shutil.copyfile` 到 `storage_path`，日志 `成片已写入 {dest}`，返回的地址就是 `/media/...`。
- 两者都没有：抛出 `没有 upload_url 或本地存储路径，无法产出可访问的视频地址`。

因此「预签名失败后退回本地」发生在创建任务、生成 `upload_url` 的时候。Worker 拿到了 `upload_url` 之后，PUT 失败不会自动改走本地文件。

回退成功后要检查：

1. Worker 日志有 `成片已写入`，路径与 payload 里的 `storage_path` 一致。这个路径是 Node 创建任务时用 Node 进程的 `STORAGE_PATH`（或 Node 的 cwd）拼出来的。Worker 若在另一台机器，或两边工作目录不同，会写到 Worker 能看到的那个路径，API 机器上的目录可能是空的。两边需要能写同一目录。
2. 目录对 Worker 进程可写。拷贝失败会变成「失败」，日志里是 Python 的权限异常，再经 `任务失败` 进入 Nest。
3. 浏览器访问的是 `public_url`，回退时就是 `/media/videos_clan-event_{id}.mp4` 这种扁平名字。本仓库的 Nest `main.ts` 和 Vite 代理没有把 `/media` 映射到 `STORAGE_PATH`（Vite 只代理 `/api`）。文件写进目录之后，还要由现网的静态服务或网关把 `/media/` 指到该 `STORAGE_PATH`，否则页面上的播放地址会 404。
4. Worker 读取事件配图时，自己的环境变量 `STORAGE_PATH` 只用于解析以 `/media/` 开头的图片（`_open_slide_image`，约第 345–355 行）。成片拷贝目标不受 Worker 这个变量影响，以 payload 的 `storage_path` 为准。

### 5. 黑屏或没字

现象：成片能打开，画面发黑，或几乎看不到中文。

代码里的原因：每一帧是 `_render_slide` 生成的 PNG，不是黑场时间轴。底色按风格取自 `CLAN_VIDEO_PALETTE`：怀旧是深棕色 `(74, 49, 28)`，现代是浅灰蓝 `(244, 247, 251)`，庄重是近黑 `(16, 16, 16)`。ffmpeg 再叠一层风格滤镜（庄重是 `hue=s=0` 去色再压暗）。输入是 `frame_%04d.png` 图片序列，从 `frame_0000.png` 起，没有 concat 文件。

字体走第三节说的 `_load_cjk_font`。字体文件都不存在或都无法 `truetype` 时，使用 `load_default()`，任务仍然成功。汉字显示为方块或 `.notdef`，庄重风格的近黑底上会更像「没字」。这不是 ffmpeg 丢帧。

配图失败不会变成全黑：下载失败打 `图片下载失败，改用文字卡: ...`，图片打不开打 `事件图片无法使用，改用文字卡: ...`，然后只画文字卡。`/media/` 图片会先在 `STORAGE_PATH`（Worker 环境变量，缺省为 Worker 进程 cwd 下的 `storage/media`）里找扁平文件名，再找保留斜杠的相对路径，都没有就用 `LIGHTHOUSE_URL + 该路径` 去下载。Worker 的 `LIGHTHOUSE_URL` 指错时，照片会退回文字卡，字仍应按字体结果显示。

排查：

1. 在 Worker 机器上按第一节的顺序确认至少一个字体文件存在，并用该用户权限能打开。
2. 看 `worker.log` 里有没有「改用文字卡」。有的话画面可以没有照片，应仍有文字；若同时缺字体，就只剩色块和方块。
3. 确认合成日志是 `生成clan-event幻灯片` 或 `生成clan-migration幻灯片`，且任务最终是 `✅ 任务完成`。ffmpeg 若失败，结果是「失败」而不是一条黑屏成片。
4. 庄重风格本身底色接近黑色，滤镜还会去色。对照同一批事件用 `modern` 看是否只是风格偏暗。

## 三、代码自检

本节只记录阅读 `handle_video` 和 `_assemble_mp4` 的结论，没有改代码。

### 空事件会不会 IndexError

结论：当前 `handle_video` 不会因为空事件下标访问而 `IndexError`。

`handle_video`（约第 496–498 行）先取 `payload.events`。不是 `list`，或是空列表，就抛 `ValueError: 视频任务缺少事件快照`，后面的 `for index, event in enumerate(events)` 不会执行。函数里没有 `events[0]` 一类下标。缺字段、`events: []`、`events` 为 `null` 或其他类型，都走这个异常，再由 `process_job` 回调 failed。

创建侧已经挡住空队列：`ClanEventVideoService.create`（约第 55–57 行）和 `ClanMigrationVideoService.create`（约第 60–62 行）在 `events.length === 0` 时抛 `BadRequestException: 指定范围内没有可生成的事件`，不会写入 `heavy_jobs`。Worker 若被单独调用，或有人改了已入库的 payload 把 `events` 清空，仍然是上面的 `ValueError`，不会 `IndexError`。列表里某一项不是对象时，循环里会把它换成 `{}` 再画一帧「未命名」，同样不是下标错误。

### 命令拼接有没有注入

结论：没有 shell 注入。ffmpeg 参数是 list，`subprocess.run` 没有 `shell=True`。

`_assemble_mp4`（约第 434–445 行）把可执行文件、`-i`、`-vf`、`-c:v libx264`、输出路径放进 list。`-vf` 的风格段来自 `CLAN_VIDEO_VF` 的三个固定字符串；用户传入的 `style` 只用来选这三档，对不上就用 `nostalgic`，原始字符串不会拼进命令。标题、地点、描述只进入 Pillow 的 `draw.text`。图片 URL 不进入 ffmpeg 参数。帧文件名是 `frame_{序号:04d}.png`，成片临时名是 `out.mp4`。

残留风险（队列里的 payload 若被改过，或图片 URL 来自可被写入的媒体地址）：

- `/media/` 配图在 `_open_slide_image`（约第 345–353 行）会做两条本地路径。扁平名把 `/` 换成 `_`，这一条不会用 `..` 跳出目录。另一条 `os.path.join(STORAGE_PATH, name)` 保留路径中的 `..`，文件存在时会被直接打开，存在读路径穿越。
- 图片 URL 既不是 `/media/` 也不是 `http://` / `https://` 时，只要 `os.path.isfile(url)` 为真，就按本机路径打开。下载目标文件名固定为临时目录下的 `photo`，下载本身不用用户字符串当文件名。
- 没有 `upload_url` 时，`_publish_video` 把成片 `copyfile` 到 payload 里的 `storage_path`，不再做文件名消毒。正常创建时这条路径由服务端拼好；payload 被改成其他路径时，Worker 会往那个路径写 mp4。
